# 数据工程 / 后端实现方案

## 1. 技术选型结论

### 1.1 36 小时推荐栈（按优先级）

| 层 | 选型 | 选择理由 | 暂不选择 |
|---|---|---|---|
| API | Python 3.12 + FastAPI + Pydantic v2 | 抓取/清洗生态完整，Schema 与 OpenAPI 自动生成，开发快 | Node 双栈会增加数据处理成本 |
| 抓取 | HTTPX + selectolax；必要时 Playwright | 静态页优先，JS 页面才启浏览器，减少不稳定性 | Scrapy 在 2–3 个源下偏重 |
| 任务 | 数据库 Job 表 + FastAPI BackgroundTasks | 单机 Demo 足够，可观察、无额外服务 | Celery/Redis 属于过度架构 |
| 数据库 | SQLite + SQLAlchemy 2 + Alembic | 单文件、无外部依赖、断网友好；JSON 以文本保存 | 云 PostgreSQL 会引入网络与账号风险 |
| 去重 | RapidFuzz + tldextract + 自定义规则 | 可解释、参数固定、适合小样本 | 向量数据库和图数据库没有必要 |
| 文本抽取 | 规则优先 + LLM 结构化输出兜底 | 证据字段可控；LLM 只抽取，不判定事实 | 全链 LLM 成本高且难复现 |
| 缓存/快照 | SQLite + `data/snapshots` 内容哈希文件 | 支持离线演示和审计 | Redis 不需要 |
| 测试 | pytest + respx + 固定 HTML fixtures | 可复现连接器、清洗、评分与 API | 只做现场手测风险高 |
| 前端协作 | React/Vite 调 FastAPI | 4 屏 Demo 足够快 | Next.js 服务端能力当前用不上 |

### 1.2 赛后迁移

SQLite → PostgreSQL；BackgroundTasks → 队列；本地快照 → 对象存储。只有并发、任务量或多实例部署证明需要时才迁移，API 与领域模型不变。

## 2. 总体数据链路

```text
Source Registry
  → Connector（抓取公开页）
  → Raw Evidence Store（URL/时间/文本/快照哈希）
  → Normalizer（语言、日期、单位、产品词）
  → Extractor（规则 + LLM JSON）
  → Entity Resolution（公司去重/母子关系）
  → Signal Truth Scoring（四维验真）
  → Buyer Requirement × Private Seller Criteria Matcher
  → Opportunity Scoring / Top 5
  → Buyer Signal API
  → 前端 4 屏
```

每层都保存输入、输出、版本和失败原因。禁止从抓取结果直接跳到 LLM 最终答案。

## 3. 数据源策略

### 3.1 来源优先级

| 优先级 | 来源类型 | 作用 | 证据强度 | 风险 |
|---|---|---|---|---|
| P0 | 公开 RFQ / 招标 / 采购公告 | 明确采购动作、规格、截止时间 | 强 | 数量少、页面结构不同 |
| P0 | 买家官网采购页、产品页、新闻稿 | 新品/扩品/供应商招募等近期变化 | 中强 | 需区分营销内容和采购意图 |
| P1 | 公开贸易/进口记录页面 | 证明历史采购行为与频率 | 中，只作背景 | 更新延迟、主体归属、可能付费 |
| P1 | 公开企业目录/注册信息 | 证明公司主体、域名、地址 | 主体证据 | 不证明采购需求 |
| P2 | 搜索 API | 发现候选 URL | 不作为最终证据 | 搜索摘要可能截断或过期 |

Demo 接 2 个稳定连接器 + 1 个可选连接器。禁止绕过登录、验证码、robots、付费墙或技术限制；遇到限制就改用人工确认的公开样本并标 `SAMPLE`。

### 3.2 Connector 契约

```python
class SourceConnector(Protocol):
    source_code: str

    async def discover(self, query: ProductQuery) -> list[DiscoveredUrl]: ...
    async def fetch(self, item: DiscoveredUrl) -> RawDocument: ...
    def parse(self, document: RawDocument) -> list[RawSignal]: ...
```

统一输出最少包含：

```json
{
  "source_code": "public_rfq_a",
  "source_type": "RFQ",
  "url": "https://example.org/rfq/123",
  "title": "...",
  "published_at": "2026-08-27T09:00:00Z",
  "observed_at": "2026-08-28T02:10:00Z",
  "text": "...",
  "snapshot_sha256": "...",
  "data_mode": "LIVE"
}
```

### 3.3 抓取参数

| 参数 | Demo 值 |
|---|---:|
| 每域并发 | 1 |
| 默认间隔 | 2 秒/请求；按站点条款更严格时从严 |
| HTTP 超时 | connect 5 秒，read 15 秒 |
| 重试 | 2 次，仅 429/5xx/连接错误，指数退避 2s/5s |
| 单页上限 | 2 MB；超出终止并记录 |
| 单次任务上限 | 每连接器 30 URL；全任务 60 URL |
| 缓存 TTL | 24 小时；演示冻结数据集永不过期但标 `CACHED` |
| User-Agent | 明确应用标识和联系信息（若站点允许） |

## 4. 清洗与标准化

### 4.1 顺序

1. 解码、去脚本/样式/导航、正文抽取。
2. 语言识别；中文/英文以外先保留原文，再按需翻译。
3. 日期解析为 UTC，另存 `time_precision` 和原始文本。
4. 公司名、域名、国家、地址标准化。
5. 产品同义词映射：如 `matcha / green tea powder` 不能无条件等同，只有上下文确认才映射。
6. 单位标准化：kg/t/lb、mm/mesh、°Brix、温度、货币；同时保留原始值。
7. 规则抽取高确定字段，再让 LLM 补充结构化字段。
8. 每个字段记录 `confidence` 和 `evidence_span`。

### 4.2 缺失与冲突

- 缺失统一用 `null + status=UNKNOWN`，禁止写 0、空字符串或“符合”。
- 两来源冲突时不静默覆盖，存入 `field_observation`；优先级为：原始采购页 > 买家官网 > 权威目录 > 聚合站。
- 日期冲突优先页面机器可读发布时间，并保留所有原始值。
- 单位换算保留 `raw_value/raw_unit/normalized_value/normalized_unit`。

## 5. 实体去重与子公司溯源

### 5.1 不可混淆原则

公司别名可以合并；母公司、子公司、品牌与运营公司不能直接合并。它们以关系表达，信号归属实际发布/采购主体。

### 5.2 特征与权重

| 特征 | 权重 | 说明 |
|---|---:|---|
| 官网注册域名完全相同 | 0.35 | 排除公共邮箱域名 |
| 标准化法律名称相似度 | 0.25 | 去公司后缀后 RapidFuzz |
| 国家一致 | 0.10 | 国家冲突强扣分 |
| 地址相似 | 0.15 | 规范街道、邮编 |
| 电话/注册号/税号相同 | 0.15 | 任一强标识命中 |

```text
entity_score = Σ(feature_match × weight)
```

| 阈值 | 动作 |
|---:|---|
| ≥ 0.92 | 自动合并别名，保存 merge audit |
| 0.75–0.919 | 进入人工复核，不自动合并 |
| < 0.75 | 保持独立 |
| 国家冲突或强标识冲突 | 无论名称多像都不自动合并 |

这些是 Demo 初始参数，不宣称为通用最佳值；需要用 20–30 组标注样本做赛后校准。

### 5.3 母子关系

关系类型：`SUBSIDIARY_OF / BRAND_OF / OPERATED_BY / ALIAS_OF`。只有 `ALIAS_OF` 可折叠为同一实体，其他关系在 UI 展示但保持独立 `buyer_id`。

## 6. 买家需求与卖家私有条件匹配

### 6.1 通用模型

每类买家需求/卖家匹配条件由 JSON Schema 描述。卖家条件只用于检索和评分，不对外生成商品展示：

```json
{
  "category": "food_ingredient",
  "product_type": "matcha",
  "product_form": "powder",
  "attributes": {
    "moisture_pct_max": {"type": "number", "unit": "%", "hard": false},
    "organic_cert": {"type": "certificate", "hard": true},
    "moq_kg": {"type": "number", "unit": "kg", "hard": false}
  }
}
```

新增品类时只增加需求模板、词典和匹配规则，不改机会表和 API 主结构。

### 6.2 三值匹配

| 状态 | 定义 | 排序处理 |
|---|---|---|
| PASS | 双方字段明确且卖家满足 | 加分 |
| FAIL | 双方字段明确且冲突 | 硬字段直接拒绝；软字段扣分 |
| UNKNOWN | 任一侧缺数据 | 不当成失败，扣少量信息完整度并生成 Gap |

证书还要同时校验：类型、适用工厂/产品、目的市场、有效期。只有一个证书名称不能判 PASS。

## 7. 评分服务

评分必须是纯函数，输入相同、规则版本相同则输出相同：

```python
score_opportunity(
    signal_snapshot,
    buyer_snapshot,
    seller_capability_profile_snapshot,
    ruleset_version="demo-1.0"
) -> ScoreBreakdown
```

输出包含 `truth_score`、四维明细、`opportunity_score`、五项明细、硬门槛结果、拒绝原因、规则版本。LLM 不能直接修改数值。

### 7.1 Agent / SKILL 运行结构

36 小时只使用一个 `BuyerHunterOrchestrator`，依次调用 6 个有固定输入输出的步骤：

```text
DemandUnderstanding
→ BuyingWindowDetection
→ SellerFitMatching
→ MarketAccessGate
→ DealActionPlanning
→ EvidenceCoverageAudit
```

每个步骤返回结构化 JSON 和完成状态，不让多个自由 Agent 相互对话。任一步需要更多证据时返回 `MORE_EVIDENCE` 并停止；准入为 `BLOCK` 时禁止生成立即报价动作。

统一机会对象至少包含：`buyer_requirement`、`buying_window`、`seller_fit`、`market_access`、`deal_action`、`evidence_coverage`、`data_status`、`access_status`、`sales_stage`。会员 `access_status` 只控制字段访问，不能修改真实性或机会分。

## 8. Buyer Signal API

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/seller-capability-profiles` | 创建/更新卖家私有匹配条件；不形成公开商品页 |
| GET | `/api/v1/matching-templates` | 获取买家需求/卖家条件的通用匹配模板及抹茶、蓝莓示例 |
| POST | `/api/v1/crawl-runs` | 按目标产品发起海外买家需求抓取；不依赖具体卖家 |
| GET | `/api/v1/crawl-runs/{run_id}` | 查询来源状态和各阶段计数 |
| GET | `/api/v1/buyer-requirements` | 查看平台已聚合、验真的海外买家需求，不含卖家 Fit |
| GET | `/api/v1/opportunities` | Top 5/候选列表与筛选 |
| GET | `/api/v1/opportunities/{id}` | 买家摘要、证据、匹配矩阵、评分、行动；未解锁不返回完整入口/联系方式 |
| GET | `/api/v1/buyers/{id}` | 标准实体、别名和母子关系；公开渠道由会员访问接口单独控制 |
| GET | `/api/v1/me/membership` | 查询当前卖家的会员套餐、有效期和剩余解锁额度 |
| POST | `/api/v1/opportunities/{id}/access-grants` | 校验会员并解锁采购入口和公开 B2B 联系方式；重复解锁不重复扣额度 |
| POST | `/api/v1/opportunities/{id}/follow-ups` | 记录卖家决定通过公开渠道自行跟进；平台不代发消息 |
| POST | `/api/v1/opportunities/{id}/outcomes` | 记录 NEGOTIATING/WON/LOST 及原因，用于闭环反馈 |
| GET | `/api/v1/health` | Demo 启动检查、DB/缓存/LLM 状态 |

统一错误格式：

```json
{
  "error": {
    "code": "SOURCE_TIMEOUT",
    "message": "source public_rfq_a timed out",
    "retryable": true,
    "request_id": "req_..."
  }
}
```

## 9. 数据库核心表

| 表 | 作用 |
|---|---|
| `source` | 来源配置、条款/robots 检查结果、启用状态 |
| `crawl_run` / `crawl_item` | 任务与单 URL 状态、计数和错误 |
| `evidence` | URL、时间、原文、快照哈希、数据模式 |
| `buyer` / `buyer_alias` / `buyer_relation` | 标准实体、别名、母子/品牌关系 |
| `signal` / `signal_evidence` | 采购/变化信号及证据链 |
| `field_observation` | 字段级来源、原始值、标准值、置信度 |
| `seller_capability_profile` | 卖家私有匹配条件：目标产品、市场、规格、认证、MOQ、产能等 |
| `requirement` | 买家规格、认证、商务和准入要求 |
| `opportunity` / `score_breakdown` | 匹配结果、分项评分、规则版本 |
| `match_result` | 字段级 PASS/FAIL/UNKNOWN |
| `membership_plan` / `seller_subscription` | 会员套餐、状态、有效期和解锁额度；Demo 不存支付卡信息 |
| `buyer_access_channel` | 已验证的采购页、联系页、公开企业邮箱及来源证据 |
| `buyer_access_grant` | 某会员对某机会的解锁授权和审计记录 |
| `seller_follow_up` | 卖家自行跟进的入口、操作时间和状态，不存私人信息 |
| `deal_outcome` | 洽谈、成交、失败及原因反馈；用户回填，不当作爬虫事实 |
| `entity_merge_audit` | 去重前后实体、特征、分数和操作者 |

## 10. LLM 结构化抽取

### 10.1 输入

只给正文片段、页面元数据和限定词典，不给其他买家数据，降低串样风险。

### 10.2 输出约束

```json
{
  "buyer_name": {"value": "...", "confidence": 0.93, "evidence_span": "..."},
  "product_terms": [{"value": "matcha powder", "confidence": 0.98, "evidence_span": "..."}],
  "buying_action": {"value": "seeking_supplier", "confidence": 0.88, "evidence_span": "..."},
  "requirements": [],
  "published_at": {"value": null, "confidence": 0, "evidence_span": null}
}
```

- JSON Schema 严格校验；最多修复一次。
- `confidence < 0.70` 的字段默认 UNKNOWN。
- `evidence_span` 必须是输入原文子串，否则字段作废。
- 抽取结果缓存键：`snapshot_sha256 + prompt_version + model_id`。

## 11. 安全、合规与可审计

- 仅采集公开 B2B 信息；不采集个人私人联系方式和敏感个人信息。
- 每个来源记录访问规则、最后检查时间、速率和停用开关。
- 快照用于内部证据审计，不对外重新发布完整受版权保护页面。
- 页面证据只展示必要短片段和原站链接。
- 联系入口必须是公开业务渠道；操作需要用户主动点击。
- 联系方式由服务端会员权限控制，不能仅靠前端遮罩；列表/普通 Buyer API 不返回受限字段。
- 同一订阅重复解锁同一机会必须幂等；额度扣减和 access grant 写入同一事务。
- 日志不记录 API Key、Cookie 或完整请求头。

## 12. 关键测试

| 测试 | 样例 | 通过标准 |
|---|---|---|
| 连接器解析 | 固定 HTML fixture | 字段、时间、证据片段一致 |
| 日期 | `2 days ago`、无日期、时区 | UTC 与 precision 正确；未知不造值 |
| 单位 | lb→kg、mesh 原值 | 标准值正确并保留原值 |
| 去重 | 同域名别名、同名不同国、母子公司 | 仅别名自动合并；母子保留关系 |
| 评分 | 边界 59/60/74/75、陈旧信号 | 分级和硬门槛正确 |
| 匹配 | PASS/FAIL/UNKNOWN、证书过期 | 硬冲突拒绝，UNKNOWN 生成 Gap |
| API | Top 5 稳定排序、404、任务失败 | 合同一致、错误结构统一 |
| 会员权限 | 过期会员、额度耗尽、重复解锁、并发解锁 | 未授权不泄露；重复/并发只扣一次额度 |
| 联系方式 | 公开企业邮箱、私人邮箱、失效链接 | 只返回可溯源 B2B 渠道；失效项标风险 |
| 离线 | 禁网启动 | 缓存主流程可完整演示且标 CACHED |

## 14. 官方准入信息的字段化依据

- 美国：FDA 说明进口食品需满足安全、卫生和标签要求；相关生产/储存设施通常需注册并提交 prior notice。FSVP 要求进口商基于风险验证外国供应商。系统因此需记录设施注册证据、进口商/FSVP 责任、危害/检测与标签状态，而不能只存一个 `FDA=true`。  
  来源：[FDA importing food](https://www.fda.gov/food/food-imports-exports/importing-food-products-united-states)、[FDA FSVP](https://www.fda.gov/food/food-safety-modernization-act-fsma/fsma-final-rule-foreign-supplier-verification-programs-fsvp-importers-food-humans-and-animals)。
- 欧盟：农残 MRL 需要按具体农产品和农药查询当前数据库；污染物由 Regulation (EU) 2023/915 等规则约束。系统应存“法规项 + 产品类别 + 有效日期 + 检测证据”，不能硬编码全球统一限值。  
  来源：[EU Pesticides Database](https://food.ec.europa.eu/plants/pesticides/eu-pesticides-database_en)、[Regulation (EU) 2023/915](https://eur-lex.europa.eu/legal-content/EN/LSU/?uri=CELEX%3A32023R0915)。
- 有机：美国有机进口需要相应 NOP 进口证明；欧盟有机进口需要电子 e-COI。只有买家/卖家声明“有机”时才作为相关硬条件。  
  来源：[USDA organic international trade](https://www.ams.usda.gov/services/organic-certification/international-trade)、[EU organic trade](https://agriculture.ec.europa.eu/farming/organic-farming/trade_en)。

# 五人最优分工与 3 号位执行手册

## 1. 五人责任矩阵

| 角色 | 唯一负责人范围 | 36 小时必须交付 | 明确不负责 | 上下游合同 |
|---|---|---|---|---|
| 1 产品 / 商业 | 场景、优先级、评分口径、会员模式、Pitch | PRD 冻结、5 分钟路演、验收决策 | 写爬虫、调模型、做 UI | 向全员发布字段定义与 Demo 脚本 |
| 2 买家情报 / 数据研究 | 合规来源、RFQ、采购记录、公司与证据 | 30–50 条候选信号及来源清单 | 清洗代码、评分代码 | 用导入模板交给 3 号；补证据工单由 3 号回传 |
| **3 数据工程 / 后端（你）** | 抓取、清洗、数据库、API、实体去重、访问权限 | **Buyer Signal API + 标准数据集 + 缓存快照** | 决定商业评分权重、写自由 Agent、做页面 | 向 4 号提供标准对象；向 5 号提供稳定 API/JSON |
| 4 AI / Agent | 意图、窗口、Fit、Gap、排序、下一步建议 | Opportunity Engine 和可解释评分 | 直接爬网页、自己维护买家主表 | 只读 3 号标准对象；评分结果写回约定表/API |
| 5 前端 / Demo | UI、交互、部署、缓存展示、演示兜底 | 可连续演示的会员解锁主链 | 在前端隐藏式实现业务权限、清洗数据 | 只消费 3/4 号冻结合同，不临场改字段 |

决策原则：一个字段只能有一个 Owner。2 号对“来源是否真实”负责，3 号对“数据是否规范且可追溯”负责，4 号对“判断是否可解释”负责，5 号对“演示是否稳定”负责。

## 2. 3 号位核心目标

把来源各异的网页、RFQ、贸易记录，稳定加工为同一种可追溯、可去重、可供评分、可权限控制的 Buyer Signal。

```text
2号原始来源
→ connector/import
→ raw_signal（原文不可变）
→ parse + normalize
→ atomic_demands（字段级证据）
→ buyer entity resolve + dedup
→ buyer_requirement
→ 4号 Opportunity Engine
→ opportunity + access API
→ 5号 Demo
```

## 3. 3 号位优先级

| 排名 | 模块 | 完成标准 | 风险 | 取舍 |
|---:|---|---|---|---|
| 1 | 数据合同冻结 | 4/5 号可用固定 JSON 开发，不再口头猜字段 | 字段反复修改导致全队返工 | 第 4 小时冻结 V1 |
| 2 | 原始信号与证据留存 | 每个关键字段能回到 URL、时间、原文片段 | 演示时无法证明真实性 | 原文和 hash 不覆盖更新 |
| 3 | 清洗与原子需求 | 类目、规格、数量、单位、目的地、截止期结构化；未知为 null | AI/正则把缺失值“补出来” | UNKNOWN 优先 |
| 4 | 实体解析与去重 | 别名合并；母子公司只关联不强并 | Top 5 被同一买家重复占据 | 规则优先，人工复核兜底 |
| 5 | API 与会员权限 | Preview 不泄露；Unlock 幂等扣额 | 前端遮罩但接口返回明文 | 权限在 API 层执行 |
| 6 | 缓存与 Golden Dataset | 断网仍能演示 36→12→5 | 现场源站验证码/限流 | 比赛不依赖实时全网 |

## 4. Buyer Signal V1 字段合同

### 4.1 原始信号 `raw_signal`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| id | UUID | 是 | 平台 ID |
| source_type | enum | 是 | `RFQ / TRADE / COMPANY_EVENT / MANUAL_IMPORT` |
| source_name | string | 是 | 来源站点 |
| source_url | string | 是 | 原始公开 URL |
| fetched_at | datetime | 是 | 抓取时间 |
| published_at | datetime/null | 否 | 原始发布时间，不猜测 |
| raw_text | text | 是 | 原文或合规摘要 |
| content_hash | string | 是 | 内容去重与版本判断 |
| dataset_mode | enum | 是 | `LIVE / CACHED / MANUAL_VERIFIED` |

### 4.2 标准需求 `buyer_requirement`

| 字段 | 类型 | 规则 |
|---|---|---|
| buyer_entity_id | UUID/null | 无法确认主体时保持 null，禁止进入高优机会 |
| product_category | string | 归一词，如 `tea_powder`，不能写死抹茶 |
| product_name | string | 如贵州抹茶、蓝莓鲜果/冻果 |
| specifications | JSON | 粒度、等级、Brix、认证、包装等品类扩展字段 |
| quantity_value / unit | number/null + enum | 单位统一，原值同时保留 |
| destination_country | ISO code/null | 目的地未知时不推断 |
| required_certifications | string[] | 只记录来源明确要求 |
| budget | JSON/null | 未披露即 null |
| deadline | datetime/null | 区分发布日期和采购截止日 |
| source_spans | JSON[] | 每个关键字段绑定 `raw_signal_id + quote + fact_level` |
| review_status | enum | `AUTO_PARSED / HUMAN_VERIFIED / MORE_EVIDENCE` |

### 4.3 实体 `buyer_entity`

`legal_name`、`normalized_name`、`domain`、`country`、`address`、`registration_id`、`parent_entity_id`、`aliases[]`、`confidence`、`review_status`。

## 5. 实体去重规则（按可靠性排序）

| 顺序 | 匹配条件 | 动作 |
|---:|---|---|
| 1 | 同注册号 | 自动合并 |
| 2 | 同企业主域名 | 自动合并，排除平台型公共邮箱域名 |
| 3 | 标准化公司名 + 国家一致 | 高置信候选，抽样复核 |
| 4 | 地址/电话一致 + 名称相似 | 中置信候选，人工确认 |
| 5 | 仅名称相似 | 不自动合并 |

母公司与子公司保留独立实体，通过 `parent_entity_id` 关联；同一买家的周期性采购不删除，按 `requirement_fingerprint + time_window` 标记为复购信号。

需求指纹建议：`buyer_entity_id + normalized_product + destination + key_specs + quantity_bucket`。跨站完全转载用 `content_hash/source_span similarity` 折叠为同一证据组。

## 6. 3 号位 API 冻结清单

| API | 消费者 | 返回重点 |
|---|---|---|
| `POST /ingestions` | 2/3 号 | 导入任务、成功/失败计数 |
| `GET /buyer-requirements` | 4 号 | 标准需求、原子字段、证据引用 |
| `GET /opportunities` | 5 号 | Top 5 受限摘要，不返回会员字段 |
| `GET /opportunities/{id}` | 5 号 | 真实性、Fit、Why Now、Gap、Gate、证据摘要 |
| `GET /me/membership` | 5 号 | 套餐、有效期、剩余额度 |
| `POST /opportunities/{id}/access-grants` | 5 号 | 幂等解锁、完整公司、采购入口、公开 B2B 渠道 |
| `POST /follow-ups` | 5 号 | `FOLLOW_UP / NEGOTIATING / WON / LOST` |

API 禁止项：Preview 返回完整公司名；由前端自行遮罩；猜测私人邮箱；相同机会重复扣额度；把 Agent 推断写进 FACT 字段。

## 7. 36 小时时间表（3 号位）

| 时间 | 工作 | 交付/验收 |
|---|---|---|
| H0–H2 | 与 1/2/4/5 号冻结字段与样例 | 1 个完整 JSON、错误样例、空值规则 |
| H2–H6 | 建表、导入模板、raw_signal 入库 | 2 号可自行导入，原文/hash/URL 可查 |
| H6–H12 | 两个 Connector 或一 Connector + 一导入器 | 至少 30 条候选进入原始层 |
| H12–H17 | Parser/Normalizer、Atomic Demand | 关键字段绑定 source span；UNKNOWN 不造值 |
| H17–H21 | 实体解析、需求去重、人工复核队列 | 约 12 个买家实体；别名/母子公司样例通过 |
| H21–H24 | 冻结 Buyer Requirement API 给 4 号 | 4 号不读网页、不读原始 HTML |
| H24–H28 | Opportunity/会员解锁/跟进 API 给 5 号 | Preview/Unlock/幂等/额度测试通过 |
| H28–H31 | 缓存 Top 5、断网 fallback | 源站断开仍能跑完整主链 |
| H31–H34 | 全队联调与数据修正 | 36→12→5 计数一致，字段不临时改名 |
| H34–H36 | 冻结数据、备份、路演值守 | 数据库快照 + JSON 快照 + 启动说明 |

## 8. 3 号位验收测试

| 测试 | 通过线 |
|---|---|
| 字段证据 | Top 5 每个关键事实都能定位来源 URL/片段/时间 |
| 去重 | 相同域名别名合并；同名不同国不误并；母子公司不强并 |
| 空值 | 未披露预算/数量/联系人保持 null/UNKNOWN |
| 权限 | 免费接口响应中不存在完整身份和联系方式字段 |
| 幂等 | 同会员重复解锁同机会只扣 1 次 |
| 额度 | 0 额度返回明确业务错误，不生成 Access Grant |
| 稳定 | Golden Dataset 连续 5 次产出相同 Top 5 输入对象 |
| 兜底 | 两个外部源都失败时返回缓存及 `CACHED` 标记，不白屏 |

## 9. 3 号位最终交付包

1. `db/schema.sql`：最小数据库模型。
2. `contracts/openapi.yaml`：前后端与 Agent 共用合同。
3. `data/golden/*.json`：缓存原始信号、标准需求、Top 5 输入。
4. `scripts/ingest_*`：两个来源或来源 + 导入器。
5. `scripts/normalize`、`scripts/entity_resolve`：可重复运行。
6. `README`：一键启动、数据模式、失败兜底和已知限制。

砍需求顺序：先砍实时抓取频率，再砍第二品类实跑，再砍复杂法规自动更新；绝不砍证据链、去重、API 权限和缓存快照。

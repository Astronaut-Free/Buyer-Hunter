# 买家猎手：项目理解与 36 小时范围

> 文档定位：项目统一口径。主投赛道三「开放创新」，同时保留赛道二「山地特色产业」的落地解释力。

## 1. 一句话定义

买家猎手不是“卖家商品展示平台”，也不是简单的海外企业名单爬虫，而是一个面向贵州卖家的 **海外买家需求情报聚合与智能撮合平台**。平台从海外公开信息中抓取采购需求，完成清洗、实体去重和需求验真，再根据卖家的私有匹配条件推荐“今天最值得联系的 5 个买家”。

## 2. 用户、问题、价值

| 项目 | 明确定义 |
|---|---|
| 平台用户/付费方 | 贵州特色产品出口企业的外贸销售、老板；卖家是买家需求情报的消费者 |
| 数据对象 | 海外买家公司、公开采购需求、产品规格、采购时点和公开业务联系渠道；海外买家当前不需要注册平台 |
| Demo 样例 | 卖家搜索“抹茶买家”或“蓝莓买家”；两者只是验证通用需求模型的例子，不是平台品类边界 |
| 当前动作 | 人工搜索、看平台询盘、查官网、翻贸易记录、复制到 Excel，再凭经验决定联系谁 |
| 具体损耗 | 信息散、真假难辨、过期线索多、规格不匹配、子公司重复、销售时间耗在低概率客户 |
| 核心决策 | 今天应该优先联系哪 5 家？为什么是现在？我能不能供？下一步做什么？ |
| 产品价值 | 把分散的海外采购信息变成可验证、可筛选、可撮合的买家需求，减少卖家自己找买家的时间 |

### 2.1 三方角色不能混淆

| 角色 | 在 Demo 中的身份 | 是否登录平台 | 提供什么 | 获得什么 |
|---|---|---:|---|---|
| 海外买家 | 被识别的采购需求主体 | 否 | 公开网页上的采购需求、规格和公开业务渠道 | Demo 不向其提供账户或商品浏览功能 |
| 贵州卖家 | 平台用户、情报消费者 | 是/演示账号 | 目标产品及可选私有供货条件 | 经过验真的买家需求、匹配解释和跟进入口 |
| 买家猎手平台 | 会员制买家情报与撮合服务方 | — | 抓取、清洗、验真、实体去重、匹配、采购入口和公开商务联系方式 | 卖家购买会员，获得持续的买家需求和撮合访问权限 |

因此，系统不存在“卖家把商品上架给买家浏览”这条链路。卖家能力字段只是私有计算输入。

数据顺序也必须正确：平台先形成独立于具体卖家的 `Buyer Requirement` 池；卖家查询或提交私有条件后，系统再生成该卖家视角下的 `Opportunity`。不能按某个卖家的商品反向伪造买家需求。

### 2.2 商业闭环

| 阶段 | 平台动作 | 卖家获得 | 收费边界 |
|---|---|---|---|
| 免费预览 | 展示受限的需求摘要、国家、产品和证据强度 | 判断平台是否有相关买家 | 不展示完整采购入口和联系方式 |
| 会员解锁 | 校验有效会员与套餐额度 | 完整需求、证据链、采购入口、可验证的公开 B2B 联系方式 | 按月/年会员或套餐额度 |
| 智能撮合 | 用卖家私有条件计算 Fit、Gap、Top 5 | 优先联系顺序与下一步动作 | 会员权益的一部分 |
| 成交反馈 | 记录跟进、洽谈、成交/失败原因 | 历史跟进与更准确的推荐 | Demo 不抽佣、不处理资金 |

平台卖的是经过处理的买家需求情报、访问效率和撮合能力，不是把公开网页原样搬运后收费。

## 3. 赛道定位

### 3.1 主投：赛道三 · 开放创新

| 评分项 | 分值 | 本项目对应证明 |
|---|---:|---|
| 创新性 | 30 | 从“找公司”升级为“判断采购窗口”；AI 用于证据结构化和销售解释，去掉 AI 后难以把异构公开信息快速统一为机会 |
| 完成度 | 25 | 一条主链能亲手点：输入目标产品/私有供货条件 → 扫描海外需求 → Top 5 → 买家详情 → 证据/缺口/行动 |
| 现场 Demo | 20 | 真跑、状态可见、结果可复核；网络失败时明确展示缓存模式，不伪装实时 |
| 作品潜力 | 15 | 从抹茶扩展到蓝莓只换产品 Schema 和规则；赛后可扩到刺梨、辣椒、酸汤等贵州特色产品 |
| 大众人气 | 10 | 30 秒看懂“从 50 条噪声到 5 个今天该追的买家” |

### 3.2 兼容赛道二，但不按赛道二扩范围

对应赛道二的“AI × 山地特色产业”：解决贵州特色农产品出口销售的具体堵点。答辩时可以讲产业价值、数据来源、成本与 100 天 PoC，但 36 小时内不增加政府驾驶舱、产业大屏或多行业功能。

## 4. 36 小时只证明一件事

**卖家输入“贵州抹茶”及少量私有供货条件 → 2–3 个海外公开数据源 → 30–50 条买家需求信号 → 清洗/去重/四维验真 → 智能匹配 → Top 5 买家 → Evidence / Why Now / Gap / Next Action。**

蓝莓仅用于证明同一套需求模型可配置复用：前端允许把目标产品切换为蓝莓，展示已缓存的蓝莓买家需求样本；不另做一套爬虫、评分器或页面。平台远期可以覆盖其他贵州特色产品，但 36 小时不为更多品类逐一开发。

## 5. Demo 成功标准

| 编号 | 可验收结果 | 通过线 |
|---|---|---|
| S1 | 数据采集 | 至少 2 个公开源；保存 URL、抓取时间、发布时间、原文片段与原始快照哈希 |
| S2 | 候选规模 | 抹茶 30–50 条原始信号，清洗后不少于 10 个候选买家 |
| S3 | 真实需求 | 每个进入 Top 5 的机会四维验真分 ≥ 60，且“证据来源”和“近期性”硬门槛通过 |
| S4 | 实体去重 | 同公司别名可合并；母子公司不误合并，而是保留 `SUBSIDIARY_OF` 关系 |
| S5 | 供需匹配 | 每个机会显示 PASS / FAIL / UNKNOWN 的规格矩阵；已证实硬冲突不得进入 Top 5 |
| S6 | 可解释排序 | Top 5 显示 Intent、Fit、Timing、Reachability、Penalty 的分项分数 |
| S7 | 可行动 | 每个机会至少给出一项下一步动作与一项缺口，不生成无法由证据支持的联系人或采购量 |
| S8 | 稳定演示 | 3 分钟内完成主路径；断网仍可用缓存数据完整演示，并清楚标记 `CACHED` |
| S9 | 会员闭环 | 非会员只能看需求摘要；预置会员账号可解锁采购入口和公开商务联系方式，并生成访问授权 |

## 6. 明确不做

- 不做全网实时覆盖，只接 2–3 个公开且可合法访问的来源。
- 不做完整 CRM、自动群发、邮件发送或 WhatsApp 触达。
- 不做卖家店铺、商品上架、商品详情或公开商品目录。
- 不要求海外买家注册或发布需求；需求由平台从公开来源聚合。
- 不接真实支付网关；Demo 使用预置有效会员和模拟到期时间。
- 不做合同、在线支付、订单、报关、物流或履约；Demo 提供需求入口、公开商务联系方式、撮合排序和成交结果记录。
- 不做复杂企业知识图谱；只做公司实体、别名和母子公司关系。
- 不做“真实成交概率预测”；当前分数是规则化机会优先级，不是统计概率。
- 不做多语言全覆盖；Demo 只处理中文/英文。
- 不绕过登录、验证码、付费墙或反爬机制。
- 不把 LLM 生成文本当证据；证据必须回链到公开原文。
- 不同时为抹茶和蓝莓开发独立流程。

## 7. 产品边界与关键区分

| 容易混淆 | 本项目口径 |
|---|---|
| 买家名单 vs 采购机会 | 公司存在不等于正在采购；必须有近期采购窗口证据 |
| 需求真实度 vs 供需匹配度 | “对方真想买”与“我们能供”分开计算，不能用 Fit 反向证明需求真实 |
| 母子公司 vs 重复实体 | 法律实体不同不合并；建立关系并将信号归属到实际发布主体 |
| 历史进口 vs 近期意向 | 历史记录只做背景与交叉印证，不单独构成近期采购窗口 |
| 法规要求 vs 买家偏好 | 法规准入、客户指定认证、产品商业规格分层存储，不混成一个“认证齐全”标签 |

## 8. 当前假设

1. 平台的数据主对象是海外买家需求；卖家能力字段仅作为私有匹配条件，不公开形成商品页。
2. 抹茶是主检索样例，默认检索 B2B 食品配料用抹茶粉需求。
3. 蓝莓是第二检索样例。Schema 支持 `fresh / IQF / dried / powder / juice`；默认用 `IQF 冷冻蓝莓`需求验证结构化匹配。
4. 公开来源允许使用公开网页、公开采购公告、企业官网/新闻和团队人工确认的公开样本；任何样本必须标注 `LIVE / CACHED / SAMPLE`。
5. 比赛规则允许公开数据、自造样例和模拟数据，但不能把模拟数据冒充实时接入。

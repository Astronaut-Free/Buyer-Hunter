# 整合架构与运行

## 1. 为什么是"一个仓库、两个运行时 + 一个静态前门"

合并前的分支状态：

| 分支 | 栈 | 内容 | 处理 |
|---|---|---|---|
| `Free` | Python | A1 采集 + A3/A4/A5 决策引擎 + API + demo | 基线 |
| `MVP` | Node.js | A2 + A6 + Agent 控制面（作者 剑锋传奇） | vendored → `agent/` |
| `ui` | 静态 HTML | 门户站点：首页 + 全球商机页（作者 yayaw2826-oss） | vendored → `site/` |
| `brand2` | Python | demo 前端并行重写（落后 Free） | 未合并，见 §9 |
| `LAY` / `main` | — | 仅初始空提交 | 无内容 |

`MVP` 和 `ui` 都从初始空提交分出，各自独立；`MVP` 只把 Free 的 5 条机会当静态种子。

**没有做跨语言移植**，因为：
- Python 适合 A1（抓取/清洗），Node 的 A2/A6 已建好、109 测试通过、有交接文档
- 全量移植 = 数天 + 破坏 ~200 个通过的测试 + 违反交接文档"不重构 A2/A6 主状态机"的约束

`integration` 分支把 `MVP` 整树 vendored 到 `agent/`、`ui` 整树 vendored 到 `site/`（都用 `git read-tree --prefix=`），只改路径不改逻辑，再用数据桥 + `nav-bridge.js` 打通。`site/` 是纯静态前门，与功能层（`demo/`）解耦——它不替代 demo。

## 2. 数据桥（Free ⇄ agent，v2 双向）

正向（Free → agent）：

```
pipeline/run_pipeline.py  (A1 collect → clean/score → aggregate)
  → pipeline/build_opportunity_store_v1.py
  → runtime/buyer_hunter.db
  → scripts/export_opportunities_for_agent.py       ← 正向桥
  → agent/db/opportunities.json  (18 条非 PASS 机会)
  → agent/server/repository.js  (启动时读入 state.opportunities)
```

反向（agent → Free，contract v2）：

```
agent/server/index.js persist()  (每次状态变更防抖落盘)
  → agent/db/agent-outcomes.json
  → scripts/import_agent_outcomes.py                ← 反向桥（幂等）
  → runtime/buyer_hunter.db
      a6_outcomes → deal_outcome（仅 bridged id；A2-only id 跳过）
      a2_targets  → agent_discovered_target（按 seed_key upsert）
      domain 命中 → buyer_alias + entity_merge_audit（AUTO_MERGE）+ matched_free_buyer_id
```

- 只导出 `decision_status != 'PASS'` 的行（与 `/api/v1/opportunities/today` 同口径）
- 字段映射与 v2 反向合同见 [`contracts/opportunity-bridge-v1.md`](../contracts/opportunity-bridge-v1.md)
- `agent/db/free-opportunities.json` 是 committed fallback（无桥输出时用）
- **merge-on-reload**：正向桥是全量覆写，agent boot 时对已有行保留 A6 变更（fields/stage/status/a6），只刷新决策/分数字段
- **domain 实体解析**：Free `buyer.domain` ⇄ A2 target domain（casefold）；命中后 agent 侧给 A2 机会绑 `buyer.free_buyer_id` + `free:buyer:<id>` 外部引用。当前 95 买家均无 domain，机制由测试证明、domain 填充后自动生效
- store 是全量原子重建，所以启动顺序恒为 `db → export → import`（`-Export` / `make up` 已内置）

## 2.5 Capability CLI 桥（A3/A4/A5：Python 权威）

V1.0 方案 Phase 5–7：A3/A4/A5 的正式逻辑在 Free，Node 侧仅保留输入适配、调度、校验、Trace 与状态持久化。A6 会话内刷新时经子进程 CLI 调 Free：

```
agent/skill-runtime/dependency-refresh.js  (异步 runner)
  → agent/skill-runtime/python-capability-runners.mjs  (execFile, 8s 超时)
  → scripts/capability_cli.py               {"capability","context"} → CapabilityResultEnvelope
  → Free: purchase timing / supply_demand_fit.evaluate / trade risk
```

- 注入：`createLiveA2A6Runtime({ dependencyRunners })`；`server/index.js` boot 探测 `python` + CLI 可跑才启用
- **失败即报错**：spawn 失败 / 非 0 / 坏 JSON / 超时 → 返回结构化 `ERROR`（`CAPABILITY_RUNTIME_UNAVAILABLE`），Node 仅负责路由、校验、Trace 与持久化
- `QIANPULSE_PYTHON_CAPABILITIES=off` 强制返回运行时 `ERROR`；`PYTHON_BIN` 覆盖解释器
- `/api/health` → `python_capabilities: "on"|"off"`
- 合同：`contracts/capability-result-envelope.schema.json` + `contracts/agent-event.schema.json`（两侧合同测试）
- 统一 Opportunity（Phase 4）设计见 `contracts/opportunity-v2.md`，尚未实现

选 CLI 不选 HTTP 的原因：Capability CLI 已由异步 `execFile` 调用，协议简单且保留独立进程边界；子进程约 200ms/次，可接受；后续瓶颈时再升级常驻服务。

## 4. 运行

| 目标 | Windows | 其他 |
|---|---|---|
| 装依赖 | `.\run.ps1 -Setup` | `make setup` |
| 建决策 store | `.\run.ps1 -Build` | `make db` |
| 数据桥（正向+反向） | `.\run.ps1 -Export` | `make export && make import` |
| 起全链 | `.\run.ps1 -Up` / `-Down` | `make up` |
| 双套测试 | `.\run.ps1 -Test` | `make test` |
| 审计 | `.\run.ps1 -Audit` | `make audit` |

`-Up` 起三个进程（demo 4173 已退役，代码保留但不再启动）：

| 服务 | 端口 | 说明 |
|---|---|---|
| **site** | `4180` | 门户前门（静态，`python -m http.server`）；商机页经 `opportunities-live.js` 拉 `/api/v1` 实时数据（失败回退静态样例） |
| demo | `4173` | 已退役（原 React/Vite 工作台，代码保留，`-Up` 不再启动；工作台已并入 agent 3317） |
| api | `8000` | FastAPI 决策读接口（CORS 含 4180） |
| agent | `3317` | A2/A6 控制面（Node）；boot 探测 Python capability；persist 时写反向桥 `agent-outcomes.json` |

用户动线：`site:4180` 首页 →「立即寻找商机」→ 全球商机页 →「登录」→ `agent:3317` 工作台（`site/nav-bridge.js` 接线，可用 `window.QIANPULSE_APP_URL` 覆盖）。

| 缺口 | 说明 |

| 单语言统一 | Node ↔ Python 移植未做；两个运行时并存（方案也不建议强制统一） |

| A5 风控深度 | 准入 + 硬冲突已归 Python；买家信用 / 欺诈 / 知识产权 / 合同履约 / 法规 Provider 未做 |

| 实网 provider smoke | 缺 Smartlead / Apollo / Trademo 凭据 |
| 卖家目录 | A4 的 `seller_sku_catalog_v1.json` 是 demo 数据（3 卖家 / 5 SKU） |
| 买方主体解析 | A1 的 51 条机会均 `QUALIFIED_PENDING_ENTITY`（法定主体未核验） |
| CLI 桥延迟 | 子进程约 200ms/次；瓶颈时升级常驻 HTTP capability 服务 |
| 门户站点 | 已接 `/api/v1` 实时数据（opportunities-live.js，LIVE/FALLBACK 回退）；残留：无 API 等价字段（生产标准/成交金额）显示「—」，上游 origin/ui 迭代需 re-sync |
